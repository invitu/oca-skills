# What reviewers flag as generated

Source: rule of these skills, from review evidence (`evidence.md`).

Reviewers recognise these patterns and ask to remove them, often naming AI
("This smells to AI", "These methods seem odd (AI assisted?)"). Once they
suspect it, they switch into "bullshit detection mode for review, which is
quite taxing" and ask the author to "make your own BS removal pass first".
`oca-dev` does that pass before handing over; `oca-reviewer` rejects on any
item below.

## Code

- Blank lines inside a method. "If you want to set logical blocks, put a
  comment line." In an existing file, follow the file.
- A helper method used once, a one-line wrapper of standard Odoo, a method
  where a dict would do: "please avoid one line functions that are being used
  once and obfuscate stuff that's very standard Odoo".
- Guards for states that cannot happen: `or ""` on a value that always exists
  ("we know that this exists"), a branch for a misconfigured Odoo,
  `if "field" in self._fields` for a module not in `depends`, retries with a
  looser match ("seems random"), code that repairs another system's bugs.
- Swallowed exceptions: "if something is wrong, raise". In a migration script
  no exception handling at all: "if some step of a migration script fails, the
  whole thing should fail".
- Ids passed where a recordset works; several passes (`filtered`, `mapped`,
  loop, `mapped`) over the same records instead of one loop with `break`.
- Long forms of short idioms: `rec.mapped("company_id").ids` for
  `rec.company_id.ids`, `x and x[0]` for `x[:1]`, `filtered(lambda r: r.f)` for
  `filtered("f")`, `else` after `return`, intermediate dicts merged at once.
- Names: verbose (`total_moves` for `move_count`), negated (`avoid_x`),
  cryptic (`pid`), not Odoo-like (`_net`/`_gross` for `_untaxed`/`_total`).
- Comments that narrate or restate the code, run over several lines for a
  one-line fix, or no longer match it: "llm-smelling comments". The why of
  something unusual is the only comment wanted.
- Options for every variant: "I think we should reduce options to the ones
  really used."
- A diff long for what it does: "99 lines for a simple name check seems too
  much."
- Rewording, reformatting, renaming or moving code outside the purpose of the
  change: "Please reduce the diff".
- Unicode punctuation (em dash, arrows, curly quotes) in code, strings and
  commit messages.

## Tests

See `tests.md`. Flagged most often of all: several new methods, a new class or
a new fixture for one fix ("Please don't bloat the test suite with another new
class generated by AI. Just add the case into the existing ones."); tests of
private or compute methods, or "synthetic" ones; mocking what can be run
("the patch fest you do here"); assertions changed so the new code passes.

## Text

- PR descriptions with headings, bold, "Summary", "Key changes", "Test plan"
  sections: see `pr-text-and-replies.md`.
- Long replies that quote the whole comment: "Please avoid all the AI text.
  Concrete and concise answers is the key for getting attention."
- "Generated with ..." footers or an AI in `Co-authored-by`: forbidden by the
  AI policy, and flagged ("you can't put 'Generated with..'").

## Process

- Code presented as working that was never run: "please only submit code you
  tested and verified to work as expected". Report what was not run.
- Pull requests for several branches at once, an issue opened next to its own
  pull request, closing and reopening pull requests for the same change,
  pinging reviewers repeatedly ("much less pushiness please").
- Repository conventions skipped because they are not written anywhere: read
  how the last merged pull requests of the repository did it
  (`oca-guidelines/guidelines/references-conventions.md`).
